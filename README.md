# Repromp

**Which follow-up prompt actually helps an LLM fix a wrong answer?**

When a language model gets something wrong, the usual move is to ask again: "try again," "that might be wrong, check it," "show your steps." This project tests which of those follow-ups actually works, and whether some of them do more harm than good.

We give a model a question along with an earlier answer (sometimes right, sometimes wrong), then re-prompt it with one of five strategies and check whether the final answer is correct. Every answer is a number, so grading is automatic and objective.

## The five strategies

| Strategy | What we tell the model |
|---|---|
| Neutral retry | Look at the question again and give your own answer. |
| Error flagging | The previous answer may be wrong. Check it and fix it if needed. |
| Targeted fix | Check one specific possible mistake (a hint about where to look). |
| Step-by-step redo | Solve it again from scratch and show the key steps. |
| Self-check | Solve it, then verify the result a different way. |

## What we measure

- **Fix rate:** how often each strategy turns a wrong answer into a right one.
- **Break rate:** how often a strategy talks the model out of an answer that was already correct.
- **Extra rounds:** whether a second or third re-prompt keeps helping, and how many more calls and tokens that costs.
- Differences across models and question types.

## Two kinds of mistakes

- **Seeded errors:** we write a worked solution with one planted mistake (a copied number, a wrong formula, a flipped sign) at the start, middle or end.
- **Natural errors:** the model's own wrong answers, collected while it answers the questions cold. This tests whether a model can catch its own mistakes, not just ours.

## The questions

Easy questions were a problem in our pilot: every model got everything right, so there was nothing to fix. The current pool has 113 questions:

- **45 from GSM8K and MATH:** standard word problems and competition math (mostly too easy now; kept as a baseline).
- **40 Simpson's paradox problems:** generated by `pipeline/generate_simpson.py`. Option A wins in every group but loses when the groups are combined, and the model has to handle that correctly.
- **28 AIME 2025 problems:** hard competition math with integer answers.

Before the main study, each model answers every question 5 times without help (calibration). For each model we only keep the questions it gets right 30–70% of the time, so there's room to see strategies make a difference.

## Models

We run models through Virginia Tech's ARC LLM API:

- DeepSeek-V4.1-Flash (high reasoning)
- gpt-oss-120b (low reasoning)
- Qwen2.5-7B-Instruct (planned; needs its own ARC GPU server)

## Running it

You need Python 3.11+ (no extra packages), an ARC API key, and the **VT VPN** (ARC blocks API calls from outside it).

1. Copy `.env.example` to `.env` and paste your ARC key in. Never commit `.env`.
2. Open the folder in VS Code and follow `VSCODE_SETUP.md`. Each step is in the Run and Debug menu.
3. Run the steps in order:

```
cd pipeline
python test_pipeline.py                                                         # software tests, no API calls
python arc_study.py run --phase preflight --config models_arc_only.json --out runs/preflight_1
python arc_study.py run --phase calibrate --config models_arc_only.json --out runs/calibration_1
python arc_study.py select --log runs/calibration_1/calls.jsonl --config models_arc_only.json --out cases_selected.json
python arc_study.py run --phase smoke --config models_arc_only.json --out runs/smoke_1
python arc_study.py run --phase study --cases cases_selected.json --config models_arc_only.json --out runs/study_1
python arc_study.py analyze --log runs/study_1/calls.jsonl --out analysis.json
```

If a run stops partway (VPN drop, crash), run the same command with the same output folder and it picks up where it left off.

## What's in here

```
pipeline/
  arc_study.py            the whole pipeline: run, calibrate, select, audit, analyze
  cases_candidates.json   the 113 candidate questions with answers and worked solutions
  generate_simpson.py     makes the Simpson's paradox questions (same seed = same questions)
  models.json             model settings (models_arc_only.json skips Qwen)
  test_pipeline.py        tests for parsing, scoring, resume, and the generator
  deviations.csv          every change to the original plan, with the reason
  rubric.md               how humans grade explanations in the audit
  README.md               detailed protocol notes
appendices/               pilot report (LaTeX) and responses to feedback
verification_simulated/   fake test-run output, for checking the code only
```

Run logs (`runs/`) stay local and aren't committed. Every call is logged in full: the prompt, the response, token counts and timing.
